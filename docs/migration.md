# 从旧安装迁移

`bun run migrate <旧安装目录>` 是正式入口，内部依次完成预检、私有暂存和发布。`migrate:plan`、`migrate:stage` 是可选的检查入口，不需要三个命令挨个执行。

迁移兼容范围以一代 `Lotus-Plugin`、二代 `Lotus-ReFactor` 的业务数据为主，并接续通用抽卡历史、面板和已适配的游戏资料。旧 ZZZ 插件目录与主目录各存的抽卡历史会合并核对，保留长编号和原字段；同一抽记录冲突时停止迁移。其他插件独有的账号、任务和内部状态不保证转换；保留原件不等于已能由新程序使用。插件代际由实际数据布局核对，不能仅凭目录名判断，二代安装也可能使用 `Lotus-Plugin` 目录。

一代账号从 `MihoyoBBSTools/config/*.yaml` 转换，二代从 `data/users/*.yaml` 导入；两代都保留账号与设备信息、档案编号和签到设置。一代旧 `push` 指向外部推送服务的配置文件，保留原值与原件，并在迁移结果中列为待核项，不转换成 QQ 群号。一代每日固定 cron 会保留原时刻；周排期、间隔执行等不能等价表示为当前每日计划的旧规则会拒绝迁移，避免增加签到次数。

## 从旧荷花指令迁移

一代和二代荷花都提供主人指令：

```text
#迁移荷花云崽
```

更新对应旧插件并重启后即可使用。一代原来迁到二代的指令已替换。指令在旧安装旁创建新目录，不覆盖已有目录，自动准备 Bun 1.4.4、子模块和依赖，包括固定版本的项目内 PM2。停旧端前会实际检查后台运行环境、旧开机托管与旧宿主内数据库。环境准备成功后，先停止旧机器人使数据稳定，再执行正式迁移、整体初始化和新端启动。新端就绪后完成交接；失败时尝试恢复旧端，结果写入迁移记录。旧安装和数据保留，不自动删除。

迁移进程独立于旧机器人，兼容前台运行和 PM2；PM2 模式只停止已核对身份的旧进程。旧端关闭后可查看安装旁 `.lotus-yunzai-migration-<旧目录名>/` 中本次运行的 `state.json`、`launcher.log` 和 `worker.log`。这些文件包含本机路径及恢复所需的私有环境，不得提交到 Git 或直接公开。

当前指令支持 Linux，需要 Git 和安装旁目录的写权限。Bun 安装使用独立目录，不修改用户 shell 配置。自动安装的 Bun 位于本次私有迁移目录中，后续运行仍会使用，应随新安装一同保留。已安装并符合版本的 Bun 可直接复用。

已确认归属的开机托管会直接接管：旧机器人专用 systemd 服务保留原启用关系，迁移进程先移到独立服务，再用专用 drop-in 切换启动配置；共享 PM2 只替换旧机器人的运行记录和持久化清单条目，其他应用保持原样。原配置私有备份，失败按原记录回滚。权限或归属无法确认时，在停旧端前拒绝交接，不进行交互式提权。旧端原本没有开机自启时不会额外开启，后台运行也不代表已配置开机自启；报告中的 `newAutostartConfigured` 反映实际承接结果。

若数据库由旧宿主自己启动，迁移会辨认实际进程、冻结写入并建立持久化检查点，再将数据和 ACL 接入新端的 `data/legacy-valkey/` 独立托管。原数据库编号和绝对过期时间保留；AOF 会在验证导入完成后恢复原模式，避免把旧 RDB 当作空 AOF 启动。新端后续启动也会恢复该实例。已经独立运行的外部数据库保持原连接，不会复制或关闭。不能确认归属、持久化格式或必要权限时拒绝停旧，避免带着不完整数据继续。

接管后仍使用 `bun run start:bg`、`stop`、`restart`、`status` 和 `logs` 运维；启动器根据私有映射控制对应 systemd 服务或 PM2 实例，并重新核对目标身份。

主人、黑白名单和访问策略沿用迁入的生效配置，初始化不会创建另一份配置遮蔽它们。验证码节点开关、顺序和 TTOCR 参数一并迁入；`server.panel_url`、`server.captcha.url` 等独立访问地址保留。旧人工服务的注册 API 与新版内部验证页不同：能确定的独立域名会迁入并列出反代待核项，无法确定的旧接口只保留原件，不尝试调用。域名对应的反代仍需指向新端。

## 实际步骤

1. **准备独立的新目录。** 克隆新项目，执行 `bun install` 安装依赖。可以先用 `bun run migrate:plan /旧安装目录` 查看旧插件分类及待处理项，这一步不导入业务数据。
2. **安排切换窗口并停旧机器人。** 保留旧安装及其配置、数据和外部数据库备份。停止会改写旧业务数据的进程，使账号、记录和计划来自同一份稳定状态。协议端可继续运行、等待重连。
3. **在新目录执行一次正式迁移：**

   ```bash
   bun run migrate /旧安装目录
   ```

   命令扫描旧插件，按策略归档旧代码、保留可兼容插件，整理账号／设备、游戏与抽卡记录、签到计划、兑换记录、群设置、订阅及媒体账号等；然后在私有暂存中应用上表的维护任务日程，最后发布到新目录。
4. **整体初始化一次：**

   ```bash
   bun run bootstrap
   ```

   补齐新程序所需的资源、模型和运行工具；已迁资料与有效缓存继续使用。迁移不会代替资源初始化。
5. **核对迁移报告和本机配置，再启动：**

   ```bash
   bun run start
   # 或后台运行：bun run start:bg
   ```

   核对协议连接、主人、访问域名及本机服务；用状态、面板、签到状态和次日计划检查导入结果。既定签到计划不重抽，停机期间到期的项目由原有到期／补跑机制处理。确认后再保持后台运行。

预检可在停旧机器人前进行；正式迁移应在数据稳定后执行。若使用 TRSS 模拟祈愿当日额度等专项快照，需要提前准备对应的导出服务和授权文件，并按专项入口传入；普通文件迁移不会凭空恢复仅存在外部服务中的状态。

## 目录和恢复约束

- 正式目标应是已安装依赖、尚未整体初始化或启动的新 Git 检出。发布不会覆盖已有的 `config`、`data`、`backup`，也不会覆盖新项目的原生插件。已用作沙盒或已初始化的目录，请另建新目录迁移，不要删除现有数据来绕过检查。
- 迁移只改新目标和同文件系统的私有暂存，旧安装不会被就地覆盖。发布期间的失败可按事务记录回滚／恢复；迁移成功后的重复执行只核对完成回执，不再次导入或重新改时间。
- 源安装的 `config/` 和 `data/` 原文件另存于新安装 `backup/migration-source/`，附文件大小和 SHA-256 清单；这是原件保全，不代表每个其他插件的数据都已转换为可用状态。符号链接不跟随，链接和特殊文件列入 `sourceSnapshot.unresolved` 待核对。荷花等旧插件目录另由插件归档保留。
- 调整前的维护任务配置另存于新安装的 `backup/migration-schedule/`。临时目录、备份和账号配置均为本机私有内容，不提交 Git。
- 旧版本留下的迁移暂存不能直接沿用新策略。遇到“旧转换规则”或“旧日程策略”提示时，先保留该暂存和备份，换一个干净目标重新准备；不要手改版本字段或把旧暂存改成“已完成”。
- 正式切换后的新业务写入不会自动反向同步回旧版。需要回旧程序时，先停新程序、对账新增记录和已执行任务，再恢复原来的服务及路由。

生产专用代理、生产自动群名片的迁移约定另行处理，不能由这里的默认配置代替。
